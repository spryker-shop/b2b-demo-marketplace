Terms used in this deck. Publish event: a note that a database row changed and the shop data must follow. Queue message: one unit of work in RabbitMQ. Worker: a PHP process that takes a batch (chunk) of messages from one queue and processes it. Storage: the key-value store (Valkey or Redis) the shop reads. Search: OpenSearch. Drain: the time until all queues are empty. Sources: tools/ps-metrics/README.md:1-30; src/Spryker/PublishAndSynchronizeMetrics/_register.php:19-43 (all hooks are registered from outside core); campaign layout README.md:204-237.

Three parts: a module records, scripts run, renderers report.

1
Module
src/Spryker/PublishAndSynchronizeMetrics
PHP, about 20 classes. Hooks into core methods and writes records. Off by default.
2
Runner and samplers
tools/ps-metrics/*.sh, *-sampler.py
Run import, publish and sync in a fixed order. Sample the broker, the stores and the containers. Collect one bundle per run.
3
Model and renderers
capacity-model.py, render-*.py
Turn bundles into a capacity model, a report, a deck and a sweep report. Never need the environment.
Collection and reporting are separate. A run writes raw records once. A report can be rendered again at any time from the same records, and a rendered page is never overwritten.

OpenTelemetry hook() wraps core methods from the outside.

  • No core class, plugin or config is changed. The hooks attach by class and method name.
  • One copy of the module works in any Spryker project with the extension.
  • Without the extension each register() returns at once. No hook, no record, no error.
  • So the first check in a new project is: extension loaded and hook() exists.

How each value is taken
  • Time: wall clock around the hooked call.
  • CPU: getrusage() at start and end, user and system.
  • Memory: memory_reset_peak_usage() at start, so the peak belongs to this batch.
  • Calls: one counter per database, key-value, search and broker call.
  • Bytes: size of the message bodies the batch received.

run-baseline.sh runs one measurement in a fixed order.

  • It fails fast on a precondition, so it never produces a number that cannot be trusted.
  • Positive control: keys and documents must be above 0 at the end.
  • Production rule: the scheduler is never paused, settings stay regular. A chunk size override is refused.
  • The runner only waits for empty queues. It touches no worker and no queue.

Six traps give a confident wrong number.

1
Exit code 0
docker/sdk cli exits 0 also when the command failed. Read the output or a result file.
2
Zero keys
DBSIZE returns 0 on KVrocks, and --scan without -n sees only db 0. Count from INFO keyspace.
3
Files lag
Files written in the container reach the macOS host late. Check inside the container or use docker cp.
4
Slow broker name
Each lookup of queue.spryker.local costs about 5 s on macOS. Use 127.0.0.1 with a Host header.
5
No Jenkins jobs
No worker starts, so the queues never drain. Run scheduler:setup.
6
Old settings file
A file left behind instruments later workers until it expires. The runner deletes it at start and end.

The harness has six known limits.

  • Message age is empty under Symfony Messenger. Only the RabbitMQ adapter carries the headers back. All other values work.
  • Local is not cloud. Process start and database calls are faster on a laptop. Cloud fixed costs are larger.
  • One scale. Linear growth is assumed until larger data is measured (customer-size files are ready).
  • Noise. Single runs differ up to 2.3x. Only campaigns are compared.
  • Samplers need Docker. Service and storage samplers use docker stats and docker exec.
  • Lab sweep. The batch-size sweep pauses the scheduler. Its figures are the cost of the work alone.
